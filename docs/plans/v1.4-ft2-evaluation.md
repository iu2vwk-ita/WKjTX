# FT2 — evaluation for WKjTX

Status: **on hold, do not implement yet.**
Written 2026-08-25 against WKjTX v1.3.0 (JTDX 2.2.159 base).

## What FT2 is

FT2 is an ultra-fast member of the FT family: a 3.75 s T/R period, half
of FT4's 7.5 s and a quarter of FT8's 15 s, carrying the same 77-bit
message payload and the same LDPC (174,91) forward error correction as
FT8/FT4, with Costas-array synchronisation. A full QSO takes 15–20 s,
which is the entire point of the mode — contest and pile-up rate.

It first appeared in February 2026, out of experiments by Martino
Merola, IU8LMC, with the ARI Caserta team.

## The blocker: there are two incompatible FT2s

| | Decodium FT2 (IU8LMC) | WSJT-X Improved FT2 (DG2YCB) |
|---|---|---|
| First release | mid-February 2026 | 26 February 2026, v3.1.0 |
| T/R period | ~3.8 s | 3.75 s |
| Source | closed, own application | GPL, source tarball on SourceForge |
| Modulation | disputed — see below | disputed — see below |

The two do **not** decode each other. Public sources contradict each
other about which set of parameters belongs to which implementation:
one pair of figures ("4 tones at 41.67 baud, Costas sync, 24 ms symbol")
and another ("2 tones at 75 baud, binary sync word") circulate with the
attribution swapped depending on who is writing. Nobody has published a
protocol document with the authority of K1JT's FT4 paper. Treat every
number in this file as unverified until it is read out of source code.

Only the WSJT-X Improved variant is implementable at all: it ships as
GPL source, which is licence-compatible with WKjTX. The Decodium
variant would have to be reverse-engineered, and its author has raised
licensing objections about exactly that.

## What implementing it would cost

The base gap is the real expense. WSJT-X Improved v3.1.0+ sits on the
WSJT-X 3.x tree; WKjTX sits on JTDX 2.2.159, and `CLAUDE.md` already
rules out rebasing on WSJT-X 3.0 (4–8 weeks, no decoder gain). So FT2
means porting, not merging.

**Fortran side.** FT4 in this tree is 15 files in `lib/ft4/` plus
`lib/ft4_decode.f90` and `lib/ft4_mod1.f90`: generator, waveform,
downsampler, baseline, candidate search, bit metrics, OSD, sync, and a
subtract routine. FT2 needs the same set, retuned for the shorter
symbol. The LDPC and OSD code is shared with FT4 and would come along
unchanged, which is the one genuinely cheap part.

**C++ side.** `m_mode == "FT4"` appears 28 times across the C++ sources
and `m_TRperiod` 73 times in `mainwindow.cpp` alone. A 3.75 s period is
below anything the sequencer, the audio buffering, the waterfall
timing and the "Tx even/1st" logic were written to assume; JTDX's
scheduler was tuned around 15 s and patched for 7.5 s. This is where
the weeks go, not in the decoder.

**Realistic estimate:** 2–4 weeks of focused work for a decode-only
prototype, more before it is safe to transmit with.

## Recommendation

Wait. Three things have to be true before the work pays off:

1. One of the two FT2s clearly wins, so we are not implementing a mode
   that half the band cannot hear.
2. A written protocol specification exists, or the WSJT-X Improved
   source is read closely enough to serve as one.
3. PSKReporter traffic shows sustained activity rather than a
   February–March 2026 novelty spike.

Re-check in a few months. If FT2 survives, the first step is a
decode-only branch: port the Fortran, add a fourth timing case, and
leave TX disabled until the receive side is proven against known-good
recordings.

Meanwhile, the cheap adjacent win is the FT8 band-hopping scheduler
noted in the improvement list — it reuses `WSPRBandHopping.cpp`, which
already exists in this tree.
